## Recovery time against log size

Checkpointing is disabled for these runs, so the whole log really is replayed.
With checkpointing on, recovery reads at most one checkpoint plus one segment
however long the store has been running, which is the point of clause B6.

| records in log | log bytes | recovery | records/sec |
|---:|---:|---:|---:|
| 100 | 15.8 KiB | 25.371ms | 3,941 |
| 1000 | 158.2 KiB | 14.503ms | 68,951 |
| 10000 | 1.5 MiB | 44.59ms | 224,265 |
| 100000 | 15.4 MiB | 144.219ms | 693,389 |

The smallest row is mostly fixed cost - opening the directory, reading the
checkpoint, creating a segment - rather than replay, which is why its
records/sec figure is so much worse. Replay itself is linear in log bytes.

## Where this loses

Against any real storage engine, on throughput, by one to three orders of
magnitude. That is the trade, not an oversight.

- **Every Put costs an fsync.** RocksDB, LMDB and SQLite in WAL mode all
  default to not doing that, and the gap is most of the difference between
  the first row above and the numbers those engines publish. The comparable
  configuration is sync=true / PRAGMA synchronous=FULL, and even there they
  win on batching, on threading, and on being storage engines rather than
  eight hundred lines of demonstration.
- **Writes are serialised behind one mutex.** There is no concurrency win
  available; the CPU count above is irrelevant to the write path.
- **The whole live key set is in memory**, so a store larger than RAM is
  not a store this can open. The read row reflects that: it is a map
  lookup and a copy with no disk in the path at all, and should be read as
  a measurement of Go's map rather than of a storage engine.
- **No compression, no block cache, no bloom filters, no range scans.**
- **These numbers come from wherever this was run.** If that was not
  Linux, they sit beside durability claims that are only proven on Linux.
  Re-run the harness there before quoting any of it as a Linux figure.
